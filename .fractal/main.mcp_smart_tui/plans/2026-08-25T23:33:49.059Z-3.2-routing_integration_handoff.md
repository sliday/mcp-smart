# 3.2 Routing Integration and Command Handoff

## Outcome

Convert the active `routing_mcp` child from an in-progress TDD effort into a
reviewed, reproducible merge on the parent branch, then create the pure
`cli_commands` child from that merged interface. Do not start command work from
the dispatcher-only baseline and do not duplicate any child-owned implementation
in the parent.

## Current state and authority

- The binding design spec remains authoritative over illustrative plan types.
- The parent dispatcher boundary is committed and its focused tests/build are
  GREEN. The only parent worktree change is the corrected present-tense memory
  state; there is no failed-step backstop or interrupted production diff.
- `routing_mcp` is active from the dispatcher commit. It has completed source
  and declaration inspection, restored the setup-induced parent-owned lockfile
  drift, and recorded the Context7 unavailability. It has not yet created its
  owned TypeScript sources or tests.
- The routing child has 2.4894 of its run cap remaining. The parent subtree has
  15.9034 and roughly 103 minutes remaining. The child has been directed to
  preserve a coherent, evidenced owned boundary before reserve rather than
  broadening scope.
- The remaining children are intentionally sequential: command functions depend
  on the merged consultation interface, and the Ink TUI depends on merged
  commands plus parent CLI wiring. Parallel spawning would create interface
  drift and predictable rework.

## Execution plan

### 1. Actively manage routing completion

1. At the start of EXECUTE, read the routing child outbox, status, spend, saved
   queue, working-tree ownership, and commits. Continue monitoring at meaningful
   step boundaries; do not poll or inspect uncommitted code as a substitute for
   a child handoff.
2. Require the child's TDD sequence to remain Tasks 2–4:
   contracts/cache identity, OpenRouter request/receipt/error normalization,
   then canonical MCP tools and hidden aliases. Its final report must name the
   verified imports/signatures/discrepancies and exact RED/GREEN commands.
3. If the child reaches reserve with unfinished work, inspect its committed
   evidence before deciding. Continue it only if a small, explicitly named
   acceptance boundary remains and a new run cap still preserves 7.0 for the
   command/TUI children plus at least 4.0 for parent integration and wind-down.
   Otherwise keep the partial branch unmerged and report the exact blocker; do
   not absorb child-owned files merely to hide a budget miss.

### 2. Review routing from committed bytes

1. Once the child reports completion or exits with a coherent commit, inspect
   `git diff main.mcp_smart_tui...main.mcp_smart_tui.routing_mcp`, its commits,
   memory, plan post-mortem, outbox evidence, and clean ownership status. Reject
   parent/sibling file changes and retain the child branch/worktree.
2. Review the binding behaviors directly in the diff:
   - Auto resolves to `openrouter/auto`, Balanced, medium cost, and exactly the
     `auto-router` plugin with restrictions inside the plugin object;
   - direct models omit the plugin, while root `session_id`, usage request, and
     metadata header are present for consultations;
   - optional provider metadata stays absent rather than being synthesized;
   - cache identity includes every specified field and `fresh` bypasses reads;
   - stable local/provider errors stop or retry under the approved policy;
   - the server advertises only three canonical tools, requires only `task`,
     preserves raw task/context bytes, returns answer plus typed receipt, and
     accepts all seven hidden aliases through the public source-compatible
     methods.
3. Verify executable artifacts from a temporary clean archive of the child
   commit. Run the four routing/MCP focused test files, the adjacent prompt
   suite, `npm run build`, and `git diff --check`. Do not print credentials,
   prompts, contexts, or authorization data while reviewing fixtures/output.
4. Merge only after all review gates pass:

   ```bash
   git merge --no-ff -m "merge main.mcp_smart_tui.routing_mcp" \
     main.mcp_smart_tui.routing_mcp
   ```

   Re-run focused tests/build on the parent, reconcile wiki links with
   `wiki lint --path=wiki`, and fold the child’s durable RED/GREEN evidence into
   topical parent memory.

### 3. Spawn the pure command child from the merged state

1. Re-read merged exported types and `SmartAdvisorServer` construction/call
   signatures before defining the command interface. Freeze those signatures in
   the child `NODE.md`; interface friction is reported to the parent rather than
   patched in parent- or routing-owned files.
2. Initialize only after the routing merge and parent verification:

   ```bash
   fractal node init cli_commands --path=/Users/stas/Playground/mcp-smart \
     --inherit=scripts,skills --agent=codex --model=gpt-5.6-terra --effort=high \
     --max-cost=2.5 --max-iter-cost=1.25 --reserve-budget=0.3 \
     --max-iters=2 --timeout=30m --step-timeout=15m \
     --max-depth=0 --max-children=0 --max-descendants=0 --local
   ```

3. Give the child exclusive ownership of `src/commands/` and
   `src/__tests__/commands.test.ts`. Its written contract requires Task 5 TDD,
   pure return values, text/JSON contracts, missing-key doctor behavior,
   multiline task preservation, stable JSON-safe errors without stacks,
   exact RED/GREEN evidence, focused tests, build, diff check, clean ownership,
   memory, outbox, and deliberate finish.
4. Commit the child seed from its worktree with `fractal commit ... --init`,
   verify branch/cap/model/ownership, and launch it in a separate command. Do
   not initialize `ink_tui` until command work has been reviewed, merged, and
   wired by the parent.

### 4. Parent command integration boundary

When the command child later becomes reviewable, apply the same committed-byte
review discipline. After merging, the parent reads the real function signatures,
adds focused RED tests in its owned `src/__tests__/cli.test.ts`, and minimally
wires them in `src/cli.ts`. Required parent proofs are JSON/text formatting,
missing-key behavior, unknown-command stability, and byte-preserving multiline
`ask` input before the Ink child is created.

## Feasibility and stop conditions

The remaining planned child caps are 2.4894 current routing capacity, 2.5 for
commands, and 4.5 for Ink, leaving about 6.4 of the current subtree budget for
parent review, CLI wiring, documentation, verification, and wind-down before
soft-cap overshoot. This is feasible only with sequential handoffs and no new
scope. Authentication, credit, model restriction, quota, or rate-limit failures
stop that provider path immediately; only transient timeout/503 documentation or
provider calls receive at most three total attempts. A routing branch without
committed spec-complete evidence is not mergeable merely because time is short.
